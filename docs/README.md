# 文档体系规范（Meta）

> **状态**：`active`（本文件是文档体系的唯一规范来源）
> **定位**：定义本仓库文档的分层、每类文档的职责边界、更新时机与命名约定。
> **适用**：所有版本。与版本级设计文档正交——那些回答"做什么、为什么"，本文件回答"文档放哪、写什么、什么时候更新"。

---

## 1. 角色模型：单 Agent

| 角色 | 职责 |
|---|---|
| **用户** | 定方向、拍板、验收、提供真实运行环境的观察 |
| **Agent** | 实现代码 + 维护全部文档 |

没有 Worker / Reviewer 分工，也没有独立的 REVIEW 文档。**代码与文档由同一个 Agent 在同一轮交付**。

判定标准：**一次变更如果没有同步更新受影响的文档，视为未完成**。文档不是交付后的补写，而是变更的一部分。

原双 Agent 体系中 REVIEW 承担的三件事，在这里分别落到：

| REVIEW 原有作用 | 现在的承载方式 |
|---|---|
| 记录缺陷清单 | `report/REPORT_*.md` 的"问题与风险"一节 |
| 驱动修复优先级 | `todo/TODO_*.md` 的优先项 |
| 对照规格验收 | 交付前自检清单（§9）+ 测试结果 |

## 2. 文档分层

```
README.md                             L0  项目是什么 / 为什么 / 怎么开始
docs/README.md                        L1  文档体系规范（本文件）
docs/vX.Y/README.md                   L2  本版本：范围、状态、里程碑、索引
docs/vX.Y/DESIGN_vX.Y_<topic>.md      L3  为什么这么做、做成什么样
docs/vX.Y/TODO_vX.Y.md                L3  下一步做什么、做到什么算完成
docs/vX.Y/COOKBOOK_vX.Y_<topic>.md    L3  怎么跑、怎么复现、怎么排障
docs/vX.Y/REPORT_vX.Y_<milestone>.md  L3  做成了什么、证据是什么、偏差与风险
<code dir>/README.md                  L4  这个目录是什么、文件怎么组织
```

原则：**越往下越具体，越往上越稳定**。上层文档可以链接下层，下层不复制上层内容。

**版本目录内拍平**：一个版本一个目录，四类文档直接放在版本目录下，不建 `design/ todo/ cookbook/ report/` 子目录。同类型有多份时靠文件名前缀区分（如 `REPORT_v0.1_m0.md`、`REPORT_v0.1_m1.md`）；只有一个版本时，版本目录本身不应超过 6 个文件，超过说明该拆版本了。

## 3. 文档类型定义

| 文档 | 回答的问题 | 必须包含 | 禁止包含 | 更新时机 |
|---|---|---|---|---|
| **根 README** | 这是什么项目、给谁看、怎么跑起来 | 一句话定位、核心设计、快速开始、文档入口 | 版本流水账、内部实验细节 | 定位或快速开始变化时 |
| **docs/README（本文件）** | 文档怎么组织 | 分层、类型定义、更新矩阵、模板 | 具体版本内容 | 文档体系变化时 |
| **版本 README** | 这个版本做什么、现在到哪了 | 范围、状态、里程碑勾选、文档索引 | 详细方案（放 design） | 里程碑状态变化时 |
| **DESIGN** | 为什么这么做、做成什么样 | 目标与非目标、约束、方案与取舍、接口、验收标准 | 任务清单、执行命令 | 设计定稿或接口变更时 |
| **TODO** | 下一步做什么、什么算完成 | 带编号任务、优先级、验收条件、对 DESIGN 的引用 | 长篇方案论证 | 每轮开工前/完成后 |
| **COOKBOOK** | 怎么跑、怎么验证、怎么排障 | 可复制命令、参数、预期输出、常见错误 | 设计论证、结果分析 | 运行方式变化时 |
| **REPORT** | 做成了什么、证据是什么 | 结论、证据（commit / trace / 测试）、偏差、风险、下一步 | 泛泛的"已完成" | 每个里程碑收尾时 |
| **目录 README** | 这个目录是什么 | 职责、文件清单、入口、依赖方向 | 设计理由、会变的命令细节 | 目录结构或职责变化时 |

## 4. 边界铁律

1. **README 不复述设计理由**：README 答 what / where / how；why 一律进 DESIGN。
2. **COOKBOOK 不含论证**：只放可执行步骤；为什么用这套步骤写进 DESIGN。
3. **REPORT 的数字必须可追溯**：每个结论标注 `commit sha`、`run_id`（对应 `traces/<run_id>.jsonl`）或测试输出；不可追溯的数字必须标注"不可比"，不能与可信数字并列。
4. **DESIGN 只写当前版本**：不写流水账，不写"曾经考虑过"（除非是影响当前取舍的约束）。
5. **时点产物不原地改**：DESIGN / TODO / REPORT 在版本关闭后冻结；要修订就写新版并加 `superseded-by:`，不覆盖历史。
6. **目录 README 只写稳定信息**：命令细节指向 COOKBOOK。
7. **不写"计划中的代码"进目录 README**：目录 README 描述现状，不描述愿望。
8. **一次变更 = 代码 + 受影响的文档**（见 §5）。

## 5. 更新矩阵

| 变更类型 | 必须更新 |
|---|---|
| 新增 / 修改核心模块 | 该目录 README；接口变化时加 DESIGN |
| 新增工具 | 目录 README + DESIGN 的工具表 |
| 新增或完成里程碑任务 | TODO（勾选 + 验收结果） |
| 里程碑收尾 | REPORT + 版本 README 的里程碑状态 |
| 运行方式 / 参数 / 环境变量变化 | COOKBOOK + 根 README 快速开始 |
| 设计取舍改变 | DESIGN（写清新旧取舍与原因） |
| 版本关闭 | 版本 README 置 `frozen` + REPORT + `git tag vX.Y-closed` |
| 文档体系变化 | 本文件 |

## 6. 命名与位置

```
docs/vX.Y/README.md
docs/vX.Y/DESIGN_vX.Y_<topic>.md
docs/vX.Y/TODO_vX.Y.md
docs/vX.Y/COOKBOOK_vX.Y_<topic>.md
docs/vX.Y/REPORT_vX.Y_<milestone>.md
<package dir>/README.md
```

- 版本目录用 `v0.1`、`v0.2`，**不按 patch 开版本**；patch 级差异用 git commit / tag 记录。
- 一个版本可以有多个 DESIGN / COOKBOOK / REPORT，按主题拆分，但每类至少一份。
- 文件名前缀大写，便于排序时把类型聚在一起。

## 7. 状态与生命周期

文档首行统一加状态头：

```markdown
> **状态**：`active` | `frozen` | `superseded-by:<path>`
```

版本生命周期：

```
planning ──> active ──> frozen
              ^           │
              └── 新版本 ──┘
```

- `active`：允许修改。
- `frozen`：版本关闭，只读；后续变更写新版本。
- 归档靠 git tag，不靠搬目录。

## 8. 版本规划

| 版本 | 范围 | 里程碑 |
|---|---|---|
| v0.1 | Agent 内核 | M0 循环 / 模型适配 / trace，M1 记忆 / 上下文 |
| v0.2 | 服务化与沙箱 | M2 FastAPI / 持久化，M3 容器池 |
| v0.3 | Skills 与 RSI | M4 YAML skills + 按需加载，M5 三档 verifier，M6 演化门禁 |
| v0.4 | 公网与评测 | M7 部署，M8 压测与评测报告 |

版本号只在**能力边界变化**时递增，不为一次重构或一个 bugfix 开新版。

## 9. 交付前自检清单（替代 REVIEW）

每轮交付前逐条确认：

- [ ] 代码能跑：`uv run pytest` 全绿
- [ ] 文档与代码一致：目录 README 描述的文件真实存在且职责一致
- [ ] 结论可追溯：REPORT 里的每个数字都有 trace / 测试 / commit 来源
- [ ] TODO 已对账：完成的打勾，未完成的写清阻塞原因
- [ ] 设计偏差已记录：与 DESIGN 不一致的地方写进 REPORT
- [ ] 没有把"计划"写进"现状"文档

## 10. 书写规范

- **语言**：根 README 用英文（面向 GitHub），`docs/` 用中文（工作语言）；引用代码标识符保持原文。
- **日期**：一律绝对日期 `YYYY-MM-DD`，不用"上周""昨天"。
- **链接**：用相对路径，保证本地和 GitHub 都能跳转。
- **表格优先**：对比、清单、状态用表格，不用长段落。
- **结论先写**：每节第一句给结论，证据在后。
- **假设要标注**：没有数据支撑的判断写"假设"，不和结论混排。

## 11. 反模式

| 反模式 | 后果 |
|---|---|
| README 变成 changelog | 新人读不到稳定信息 |
| DESIGN 写成 TODO | 没有取舍依据，后续无法判断改动是否合理 |
| REPORT 只写"已完成" | 无法复现，无法判断是否真的完成 |
| 目录 README 复制根 README | 两处内容打架，必然过期 |
| TODO 不写验收条件 | "完成"没有判定标准 |
| 文档写给面试官而不是维护者 | 空话多、可执行信息少，反而显得没做过 |
| 代码改了文档不动 | 文档从资产变成负债 |
